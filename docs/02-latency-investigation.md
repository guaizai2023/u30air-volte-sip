# 单向延迟排查全记录

> 现象：SIP 呼出到手机，**对方说话我这边秒回**，但我说话到对方那边有延迟；
> 且**通话持续一分钟后延迟明显变长**（2~3 s → 10 s）。
> 最终定位：DSP 注入通路的**速率失配导致累积型积压**。
> 解法：有界播放队列，延迟封顶 200 ms。

---

## 0. 先建立一个正确的模型

两个方向走的是**完全不同的硬件通路**，这解释了为什么延迟是单向的：

| 方向 | 通路 | 特征 |
|---|---|---|
| 对方 → 我 | `FE_ST_DUMP`（48 kHz 采集）→ 6:1 抽取 → Asterisk | 不经过 DSP 注入，实测 20 ms 稳定，**秒回** |
| 我 → 对方 | Asterisk → 8k→16k 上采样 → `FE_ST_VOICE_PCM_P`（16 kHz 注入）→ DMA → DSP 上行 FIFO → VBC → 基带 | 积压全在这一段 |

关键事实（来自 `mu300-voice` 上游源码注释）：

- `FE_ST_VOICE_PCM_P` 按 **16 kHz** 消耗；
- 调制解调器每 20 ms 从 DSP 读走 **200 字节上行**（≈ 8 kHz 的有效载荷）。

即：我们**必须刚好跑满 32 kB/s** 才能与 DSP 的消费速度持平，**一点余量都没有**。

---

## 1. 逐层排除

### 1.1 RTP / 网络

抓包 60 秒：RTP 严格 20 ms 一包，抖动 p95 ≈ 22 ms，无丢包、无乱序。

**结论：排除。**

### 1.2 对端手机 / 运营商

用户实测：**换被叫号码、换接收设备，延迟完全一致。**

**结论：100% 在发送端设备内部，排除对端。**

### 1.3 桥接进程自身

从 `recv()` 拿到帧到 `write()` 进管道，耗时约 0.1 ms。

**结论：排除。**

### 1.4 Linux 管道

Linux 默认管道缓冲 64 KB。按 16 bit / 16 kHz 计算 = **32 kB/s**，
`64 KB ÷ 32 kB/s = 2 秒` —— 与用户最初报告的"2 秒以上"高度吻合，是头号嫌疑。

实验：进程启动后对 `aplay.stdin` 与 `arecord.stdout` 调用

```python
fcntl.fcntl(fd, F_SETPIPE_SZ, 4096)   # 压到 4 KB ≈ 128 ms
```

日志确认生效：

```
aplay-stdin 管道缓冲: 4096 字节
```

**结果：写阻塞仍是 19.3 ms，延迟没有任何变化。**

**结论：管道不是元凶，排除。**

### 1.5 ALSA 用户层缓冲

aplay 回显的 hw params：

```
exact rate : 16000 (16000/1)
buffer_size: 960      ← 60 ms
period_size: 320      ← 20 ms
```

已经压到接近下限。写阻塞 19.2 ms 属于**正常的实时节拍**（写 20 ms 就被节流 20 ms），不代表积压。

**结论：排除。**

### 1.6 ALSA 驱动层

通话中每 2 秒读 `/proc/asound/card1/pcm53p/sub0/status`：

```
avail_max : 640
hw_ptr    : 35200
appl_ptr  : 36160
delay     : 960
state     : RUNNING
```

全程 `delay` 稳定在 640~960 帧（**40~60 ms**），`hw_ptr` 紧跟 `appl_ptr`，无漂移。

> 如果延迟在驱动层，`hw_ptr` 会持续落后于 `appl_ptr`，`delay` 会越涨越大。**它没有。**

**结论：驱动层干净，排除。**

### 1.7 DSP 注入段 —— 真凶

到这一步，剩下的唯一可能就是 DSP 注入之后。

之前所有观测都指向"速率是匹配的"：aplay 稳定以 32 kB/s 被消耗、驱动 `delay` 恒定。
但用户的主观描述是**延迟随时间增长** —— 这是**累积型积压**的典型特征，说明某处存在持续的微小速率差。

于是加了一个`有界队列 + 丢帧计数`作为探针：

```
downlink 线程：只负责 recv() 入队
writer  线程：出队 → 上采样 → 写 aplay
队列上限 MAXQ = 10 帧（200 ms），超限丢最旧
```

实测结果（一通 90 秒以上的通话）：

```
| socket队列 均0 峰0 B | 播放队列 0 丢617
```

- `丢617` 帧 ≈ 12.3 秒的音频被丢弃 —— **说明我们送入的速度确实快于 DSP 的消费速度**；
- `socket队列 均0` —— 说明积压**不在** socket，Asterisk 发送节奏正常；
- 延迟被队列上限**封顶在 200 ms**，不再随通话时长增长。

**结论：DSP 注入通路的有效吞吐略低于 32 kB/s。这是固件/DSP 侧的固有特性，
用户态无法把它的消费速度调快，只能控制"送进去的量"。**

---

## 2. 为什么会出现速率失配

- Asterisk 的 8 kHz 时基来自系统时钟 / RTP 时间戳；
- DSP 的 16 kHz 注入时基来自音频子系统自己的晶振/PLL；
- 两者不同源，哪怕只有 0.3%~0.5% 的偏差，一分钟就能攒出 100~300 ms，十分钟就是数秒；
- 由于我们把 8k 硬上采样成 16k，**没有任何余量**去吸收这个偏差，误差只能全部变成积压。

> 这也解释了为什么"接收端秒回"：反向通路是 48k→8k 抽取，采集侧永远"读得比写快"，
> 队列空就等待，不会累积。

## 3. 最终方案

```python
# 读 socket 与写声卡解耦
MAXQ = 10                     # 200 ms

# downlink 线程
with inqlock:
    inq.append(p)
    while len(inq) > MAXQ:
        inq.popleft()          # 丢最旧，延迟封顶
        stat["drop"] += 1

# writer 线程
p = inq.popleft() if inq else None
if p is None:
    time.sleep(0.004)
    continue
up, prev = upsample2(p, prev)
play.stdin.write(up)
play.stdin.flush()
```

**效果**：单向延迟稳定在 200~300 ms，通话一分钟后不再恶化，双人对话可以正常进行。

**代价**：该通电话累计丢弃 617 帧（约 12 秒）的陈旧音频，具体分布未逐秒记录，
但从体验上看只表现为极轻微的吞字，正常语速下基本察觉不到。

## 4. 仍未解释的现象（诚实记录）

上游注释写"每 20 ms 读走 200 字节上行"，若按 16 bit 单声道换算只有 100 samples = 6.25 ms 的音频，
与 16 kHz 的 320 samples/20 ms 不成 2:1。这条比例关系我们**没有完全对上**，
可能 200 字节指的是压缩后的 VBC 载荷，而非线性 PCM。

这不影响结论（丢帧计数已经实证了吞吐不足），但值得后续用 DSP 侧寄存器或更底层的 trace 再确认。

## 5. 复现这套观测

桥接程序内已内置全部探针，无需额外工具：

| 指标 | 来源 | 判读 |
|---|---|---|
| 写阻塞 均/峰 | `writer` 线程计时 | 稳定 ≈ 20 ms 属正常节拍 |
| 读间隔 均/峰 | `uplink` 线程计时 | 稳定 ≈ 20 ms 说明采集正常 |
| 驱动延迟 | `/proc/asound/card1/pcm53p/sub0/status` | 持续 > 100 ms 或 `hw_ptr` 落后 → 驱动积压 |
| socket 队列 | `ioctl(FIONREAD)` | 持续增长 → Asterisk 发得更快 |
| **播放队列 / 丢帧** | 有界队列计数 | **丢帧持续增长 → DSP 吞吐不足（本次结论）** |
